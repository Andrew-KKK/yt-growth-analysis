# yt-growth-analysis
**YouTube 頻道經營與成長影響力分析系統**

這是一套 YouTube 數據自動化採集系統。專為追蹤 VTuber 與影音創作者的成長趨勢，以及即時直播熱度所設計。

🤖 **AI 協作聲明：此專題主要是由本人發想核心概念與研究目標，並由 AI 輔助建構系統架構與實作程式碼。**

## **💡 專案背景與目標**

在 YouTube API 的每日免費配額限制下（10,000 Units），本專案盡力滿足「大樣本數」與「高解析度（即時同接人數）」的需求。

本專案透過重新設計**資料庫架構**與**雙系統排程邏輯**，打造出一個在全免費資源下，**足以支持每 30 分鐘記錄約 200 個頻道狀態，並能持續運行3個月以上**的數據採集管線。

本專題的核心目的，是**嘗試從這些高頻率的追蹤記錄裡，分析出影響頻道成長的關鍵因素**，並為後續的「頻道經營分群 (Clustering)」與「特徵工程」紀錄足以用來分析的資料。

## **🗄️ 系統架構與資料庫設計**

本系統由三個核心組件構成，透過資料庫作為溝通橋樑，達成數據與執行狀態的同步。

### **1. 系統組件角色說明**

- **核心執行端 (GitHub Actions)**：負責執行核心 Python 數據採集腳本。它扮演「勞動者」的角色，根據觸發指令向 YouTube API 請求數據，並將結果寫入資料庫。
- **資料儲存與狀態中心 (Supabase)**：負責儲存所有的歷史日誌與影片數據，同時存放「查詢狀態鎖」。它是系統的「記憶中心」，確保不同來源的執行指令不會發生衝突。
- **監控與觸發塔台 (n8n 伺服器)**：部署於自建 Linux 伺服器。負責定時發送精準的觸發訊號，並執行「雙重異常狀態監控機制」。它是系統的「指揮中心」，確保任務準時啟動並通報執行中斷的異常，但仍保留 GitHub Actions 極不準時的定時觸發以避免 n8n 伺服器故障停機造成系統運作中斷

### **2. 系統運作流程概略**

1. **觸發啟動**：由 n8n 伺服器發送指令給 GitHub Actions 啟動採集。
2. **狀態檢查**：Python 腳本啟動後，優先檢查資料庫內的「鎖」與「執行間隔管制」紀錄，確認安全後才上鎖執行。
3. **數據採集**：依照「高低頻分流邏輯」向 YouTube 請求數據。
4. **解鎖與存檔**：完成數據寫入後解除資料庫鎖。若執行中途崩潰，則由監控塔台偵測並發送警報。

### **3. 資料表設計 (Schema)**

| **資料表 (Table)** | **說明與職責** |
| --- | --- |
| yt_channels | 頻道母表（包含 ID、標題、自定義網址）。 |
| yt_videos | 影片目錄，透過批次更新維護近期最新影片的數據。 |
| yt_stats_daily | 成長快照日誌，記錄訂閱與觀看成長（獨立紀錄，不受刪除操作影響）。 |
| yt_live_logs | 即時同接日誌，記錄影片 ID 與當下觀看人數，支援熱度趨勢分析。 |
| tags / channel_tags | 標籤系統。於特徵分群時使用。 |
| github_actions_logs | 任務執行紀錄表。記錄每次採集任務的狀態、觸發來源與時間，用於實作資料庫鎖與執行間隔管制。 |

## **🚀 設計亮點**

### **1. 依資料變動頻率進行雙軌採集**

- **高頻率採集 (每 30 分鐘)**：專注捕捉直播瞬間的即時觀看人數，用於繪製直播聚人與留存曲線。
- **低頻率快照 (每 3 小時)**：記錄頻道的訂閱數與總觀看數成長，並更新頻道最新影片的動態迴響數據（觀看數、按讚數、留言數）。

### **2. 自建排程伺服器與資料庫狀態鎖**

- **自建排程塔台**：為解決公有雲排程（如 GitHub Actions）常態性發生 30 分鐘不等的延遲問題，本專案部署了一台自建的 Linux 伺服器，作為系統的核心觸發器，確保極致的排程精準度。
- **內網穿透安全連線**：為了保護自建伺服器不暴露於公網，使用 Tailscale 來避免將伺服器暴露至公網的風險。雲端的虛擬機 (GitHub Actions) 在執行期間，會透過金鑰短暫加入私有內網進行通訊，任務結束後無痕註銷。
- **資料庫互斥鎖與執行間隔管制**：建立在地端與雲端雙系統協作的基礎上，為防範排程交錯引發的執行衝突，於資料庫實作了狀態鎖。若距離上次執行小於 25 分鐘，系統將自動中止任務，避免 API 配額重複浪費；同時提供手動強制執行的參數，保留維運彈性。
 
### **3. 雙重異常狀態監控機制**

為避免腳本執行中斷導致「鎖」無法解除，於 n8n 上構築了兩道防護網：

- **即時事件監控**：程式啟動並上鎖時，會主動發送通知給監控伺服器啟動 10 分鐘倒數，若超時未收到解鎖訊號，即發送電子郵件警報。
- **定時巡邏監控**：監控伺服器每 15 分鐘主動掃描資料庫，捕捉若程式中途崩潰留下的「逾時未解除鎖定紀錄」。
- **自動修復機制**：下一次排程啟動時，程式會自動識別出超過 10 分鐘仍未解除的鎖，判定為前次任務異常，並強制收回鎖並重新採集。

### **4. 資料不可變性設計**

- 避免傳統資料庫的「外鍵連鎖刪除」導致歷史資料遺失。將同接日誌與每日快照設計為不可變的歷史事實，即使未來移除了母表中的某個頻道或影片，歷史的數據紀錄與成長曲線依然會被完整保留，確保分析結果的完整性。

## **🛠️ 技術棧**

- **語言**: Python 3.11
- **核心套件**: google-api-python-client (YouTube Data API v3), supabase
- **自動執行與監控**: GitHub Actions, n8n (Webhook)
- **基礎設施**: 自建 Linux Server (搭載 Tailscale, docker, n8n)
- **資料庫**: Supabase (PostgreSQL)
